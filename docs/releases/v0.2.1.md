# whirl v0.2.1

The release that lets the CLI answer about itself. These are the notes for the
tag `v0.2.1`: the tag is cut on `main`'s tip after this file lands there, and
`.github/workflows/release.yml` builds the three archives from that tag and
publishes this file as the release notes. The release date and the tagged commit
are the tag's, not this file's, and that is why neither is written here.

Artifacts, one per platform, each holding the three binaries (`whirld`, `whirl`,
`whirl-worker`) and nothing else:

- `whirl-v0.2.1-linux-x86_64.tar.gz`
- `whirl-v0.2.1-macos-arm64.tar.gz`
- `whirl-v0.2.1-windows-x86_64.zip`

Each archive is published beside its own checksum, the same file name with
`.sha256` appended, written by the same run that built the archive.

The archive is the install. There is no installer, no `.pkg` and no signing
(`docs/development.md` section 5).

## What changed since v0.2.0

- **`whirl --version`** (and `-V`) names the binary's own version and exits. It
  opens no socket, reads no config and needs no daemon, which is the point: it is
  the answer to "which build is this" when the thing you are diagnosing is the
  daemon that will not start. `whirl version` keeps its own meaning, the
  human-readable block, and now leads with the client's half.
- **`whirl version` answers about the client when the daemon cannot be reached.**
  It now prints the client's own version and the protocol version this binary
  speaks before it resolves any socket, and then the daemon's lines when the
  daemon answers. With no daemon it prints the client's lines on stdout, the
  reason on stderr, and exits `2`, the code the CLI already used for an
  unreachable daemon; the usage text documents that. Before this, the command
  printed only the socket error and nothing about the binary that had just been
  run, which made it useless in exactly the case it exists for.
