# whirl v0.2.0

The release that gives the daemon a lifecycle, and the release whose archives can
be verified. These are the notes for the tag `v0.2.0`: the tag is cut on `main`'s
tip after this file lands there, and `.github/workflows/release.yml` builds the
three archives from that tag and publishes this file as the release notes. The
release date and the tagged commit are the tag's, not this file's, and that is
why neither is written here.

Artifacts, one per platform, each holding the three binaries (`whirld`, `whirl`,
`whirl-worker`) and nothing else:

- `whirl-v0.2.0-linux-x86_64.tar.gz`
- `whirl-v0.2.0-macos-arm64.tar.gz`
- `whirl-v0.2.0-windows-x86_64.zip`

Each archive is published beside its own checksum, the same file name with
`.sha256` appended, written by the same run that built the archive.

The archive is the install. There is no installer, no `.pkg` and no signing
(`docs/development.md` section 5).

## What changed

- **The daemon has a lifecycle, and whirl owns it.** `whirl daemon
  install|uninstall|start|stop|status` writes a per-user launchd job, hands it to
  the supervisor, takes it back out, and reports what the supervisor says about
  it. Nothing here spawns `whirld`: `whirl daemon start` asks the supervisor to
  run the job the supervisor already owns, so the supervisor stays the only thing
  that can have a daemon. This is the half that was missing in v0.1.0, where
  nothing installed a unit and no frontend was allowed to start one, so after a
  reboot nothing started the daemon at all. macOS only: the per-user Task
  Scheduler task and the `systemd --user` unit are deferred, and a platform
  without one refuses in one sentence and exits `1` rather than growing a
  half-written unit.
- **The frontend contract is amended to match.** whirl's
  `docs/architecture.md` section 8 now says what a frontend may do about the
  lifecycle: it may ask, through the daemon's own command, and it must never
  spawn a daemon of its own. The intent of "must never" item 3 is unchanged (one
  daemon, and the supervisor decides); the amendment makes the asking possible.
  The frontend release that uses it is `whirl-ui v0.2.0`.
- **`whirld` re-reads its config on every rotation.** A config edited under a
  running daemon takes effect at the next rotation instead of needing a restart,
  and a rotation that finds an unreadable file reports it rather than rotating on
  stale values.
- **A release publishes a checksum beside every archive, or it does not
  publish.** The release job writes a checksum file next to each archive and
  refuses a partial set. v0.1.0 published the three archives and no checksums,
  and each one had to be attached by hand afterwards; the frontend's installer
  verifies every archive it downloads against the checksum published beside it,
  so an archive published without one is an archive nobody can install.

## Per-platform checklist results

CI cannot prove that a wallpaper changes (`docs/development.md` section 3, "What
CI cannot prove"), so these rows come from real hardware and name the person who
ran them. A release waits for the rows, not for a green pipeline.

### macOS

- checklist: `docs/research/macos.md`, including the unverified list
- signed and notarized: no. The archives are unsigned on all three platforms,
  exactly as `.github/workflows/release.yml` builds them
  (`docs/decisions/0001-macos-artifacts-ship-unsigned-in-v0.1.0.md`). A
  downloaded tarball still needs `xattr -d com.apple.quarantine ./whirld ./whirl
  ./whirl-worker` in the directory it was extracted into, or the same thing
  through System Settings, Privacy & Security.
- run by: nobody, for this release. The macOS checklist was not re-run for
  v0.2.0. The setter row that would carry it is v0.1.0's and is unchanged: this
  release touches no code in
  `crates/whirl-worker/src/backend/macos.rs`, so what v0.1.0 verified there still
  describes it.
- what this release does add on macOS, and how it was checked: the five
  `whirl daemon` subcommands and the unit they write. The repository's own suite
  covers the unit's content, the refusals, and each step's exit code, with a
  stand-in for the supervisor rather than a real one. The app release's
  integration tests drive the same commands with a stand-in `whirl` on `PATH`
  that records every call, which is what makes the app's half evidence rather
  than a claim. **Not proven anywhere here: a real login.** No machine has yet
  been rebooted to watch this unit start a daemon.

### Windows

- checklist: `docs/research/windows.md`, "What must be tested on real Windows

- run by nobody, on no machine: the Windows setter is **not implemented**, as in

  What this release adds on Windows is a refusal: `whirl daemon install` prints

### Linux

- checklist: `docs/research/linux.md`, the section for each desktop environment
- run by nobody, on no distribution: the Linux setter is **not implemented**, as

## Config and protocol changes

Checked rather than assumed, against v0.1.0:

- **The config schema did not move.** `config_schema` is `1` in v0.1.0 and `1`
  here. No key was added, removed, renamed or given a different default.
- **The protocol version did not move.** `PROTOCOL_VERSION` is `2` in v0.1.0 and
  `2` here; no verb was added and no error code changed. The lifecycle is a CLI
  surface and not a protocol one: `whirl daemon …` talks to the supervisor, never
  to the socket, which is why a client that knows nothing about it is unaffected.
- **The state directory did not move.** The config, the state files, the socket,
  the cache and the log are at the paths `docs/spec/state-and-cache.md` gives,
  unchanged.
- **One behaviour changed with no schema change:** `whirld` re-reads the config
  on each rotation instead of holding the one it started with.

## Upgrades and known issues

- **Upgrading from v0.1.0: replace the binaries, then install the unit.**
  Replacing the three binaries is the whole upgrade; nothing in the state
  directory or the config file has to change. For a daemon that comes back after
  a reboot, run `whirl daemon install` once: it writes
  `~/Library/LaunchAgents/com.guruor.whirl.plist`, loads it, and `whirl daemon
  status` reports what the supervisor says. A running daemon holds its lock and a
  new one refuses to start while the old process holds it, so stop the daemon you
  have (through `whirl daemon stop`, or the way you started it) before replacing
  `whirld` under it.
- **Known issue: `whirl daemon install` is macOS only.** On Windows and Linux it
  prints one sentence naming the platform and exits `1`. Those units are
  deferred, not forgotten.
- **Known issue: the unit names an absolute path.** The unit it writes points at
  the `whirld` beside the `whirl` that ran the command, so extract the archive
  somewhere it will stay. Moving the binaries afterwards means running `whirl
  daemon install` again from the new location.
- **Known issue: Windows and Linux have no setter**, unchanged from v0.1.0, with
  the same user-visible refusal and the same `WHIRL_BACKEND=noop` escape.
- **Deferred:** Developer ID signing and notarization for the macOS artifact, any
  installer or `.pkg`, a Windows signing route, Linux distribution packages, and
  the Task Scheduler and `systemd --user` units.
