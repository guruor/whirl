# whirl v0.1.0

The first release. These are the notes for the tag `v0.1.0`: the tag is cut on
`main`'s tip after this file lands there, and `.github/workflows/release.yml`
builds the three archives from that tag and publishes this file as the release
notes. The release date and the tagged commit are the tag's, not this file's, and
that is why neither is written here: the notes are written on `development`
before the tag, so that the tagged commit already contains them
(`docs/development.md` section 5).

Artifacts, one per platform, each holding the three binaries (`whirld`, `whirl`,
`whirl-worker`) and nothing else:

- `whirl-v0.1.0-linux-x86_64.tar.gz`
- `whirl-v0.1.0-macos-arm64.tar.gz`
- `whirl-v0.1.0-windows-x86_64.zip`

The archive is the install. There is no installer, no `.pkg` and no signing
(`docs/development.md` section 5, "Signing, notarization and packaging: what the
research settled").

## What changed

This is the first release, so there is no previous version to compare against and
no upgrade to describe: everything below arrived with it. `main` carries the Cargo
workspace (`whirl-core`, `whirld`, `whirl-cli`, `whirl-worker`, the four members
`docs/README.md` names) and nothing that a rotation needs. What ships now:

- **On macOS, a rotation changes the desktop picture.** `whirld` spawns one
  `whirl-worker` per rotation; the worker picks a candidate, materialises it, and
  gets the pixels onto the screen through
  `-[NSWorkspace setDesktopImageURL:forScreen:options:error:]`, called once per
  screen in `NSScreen.screens` order, reached by hand through the Objective-C
  runtime because v0.1 has no third-party dependency
  (`crates/whirl-worker/src/backend/macos.rs`; `docs/architecture.md` 1.6 and
  1.7; `docs/development.md` section 7).
- **Two kinds of source, both config entries and neither a compiled-in
  provider.** `local` walks a folder of your own pictures, in `reference` mode by
  default so the file it sets is your file; `wallhaven` searches the site's API or
  one collection. `whirl sources` lists what loaded, with its weight, its last
  outcome, and the reason it is disabled (`docs/spec/features.md` Part 2, schema
  in 2.2 and 2.3).
- **A filter pipeline, a cache and a bounded history.** Resolution, aspect ratio,
  size, content type, then two dedupe passes, and the image is stored under its
  content digest; the cache has a file and a byte cap and a sweep; a ring of the
  last 50 rotations backs `whirl prev` and `whirl history`, and favorites are
  records pinned against eviction (`docs/spec/features.md` Part 1 and 2.5,
  `docs/spec/state-and-cache.md`).
- **A schedule you configure, and pause.** `schedule.interval_seconds` (1800 by
  default) and `startup.*`, including re-applying the last entry at startup and
  not overwriting an image you set by hand; `whirl pause` and `whirl resume` stop
  and re-arm the schedule and leave the current picture alone
  (`docs/spec/features.md` F4 and F9).
- **A control surface that is the CLI, over the line protocol.** `whirl status`
  prints one block of `key: value` lines, `whirl config check` prints the
  effective plan plus what each source admitted and what each filter removed,
  and `whirl next`, `prev`, `set`, `history`, `favorites`, `sources`, `pause`,
  `resume`, `idle`, `version`, `ping` and `help` are the verb set
  (`docs/architecture.md` 2.9 to 2.11; `docs/spec/features.md` 1.1).
- **One config file, JSON, with the defaults written out as comments.** Any key
  whose first character is `_` is a comment, so the file the daemon generates is
  annotated in place. Five environment variables relocate the config, the socket,
  the state and the cache, which is what makes a rotation testable without
  touching a real desktop (`docs/architecture.md` 4.1 to 4.3;
  `docs/development.md` section 7, "The five environment variables").
- **State and cache where each platform puts them**: `~/Library/Application
  Support/whirl` and `~/Library/Caches/whirl` on macOS, `$XDG_CONFIG_HOME`,
  `$XDG_STATE_HOME` and `$XDG_CACHE_HOME` on Linux, `%APPDATA%` and
  `%LOCALAPPDATA%` on Windows (`docs/spec/state-and-cache.md` 1.1 to 1.3).
- **A front door.** `docs/quickstart.md` is one page and hands-on: install, point
  it at a folder, rotate, stop. `docs/README.md` is the index of the rest, and
  `docs/development.md` is the guide to building, testing and shipping it.
- **One gate, one command per check.** `./scripts/ci.sh` has a mode for each CI
  job, so a local run and a CI run are the same commands (`docs/development.md`
  section 3). Nothing in this release sets a real wallpaper in a test: the gate
  runs the suite with the noop backend, which runs every stage but the platform
  setter.

## Per-platform checklist results

CI cannot prove that a wallpaper changes (`docs/development.md` section 3, "What
CI cannot prove"), so these rows come from real hardware and name the person who
ran them. A release waits for the rows, not for a green pipeline.

### macOS

- checklist: `docs/research/macos.md`, including the unverified list
- signed and notarized: no. The three archives are unsigned on all three
  platforms, exactly as `.github/workflows/release.yml` builds them
  (`docs/decisions/0001-macos-artifacts-ship-unsigned-in-v0.1.0.md`). The
  first-run step that costs, on a downloaded tarball: macOS puts the quarantine
  attribute on what the archive extracts, so the first run of `whirld`, `whirl`
  and `whirl-worker` needs it cleared, `xattr -d com.apple.quarantine ./whirld
  ./whirl ./whirl-worker` in the directory you extracted into, or the same thing
  through System Settings, Privacy & Security. What is verified about first runs
  is narrower than that step: a binary built on the machine raises no dialog at
  all, across the 13 writes `docs/research/macos.md` 8 records (5 through
  AppleScript, 8 through AppKit, zero prompts, and the setter needs no
  entitlement). The download path itself is unverified: no built binary has been
  taken from a release on this platform yet, so the exact dialog text and the
  exact control have not been observed here.
- run by Guru (the project owner) on a Mac15,3 (Apple M3, 8 cores, 24 GB), macOS
  26.5.2 (25F84), on 2026-09-29, through an automated session he directed; no
  human hand drove the keyboard. Result: 13 of the checklist's probe items passed,
  0 failed, 7 items were not run. The binaries were built from this release's tree
  and installed into a prefix of the run's own, two real rotations went through
  the native backend, and each change was read back from the wallpaper store
  rather than from whirl's own stdout.
  - passed: [V1] the filesystem probes; [V2] the provider names, with the
    correction recorded below; [V3] which store layers exist and which carry a
    `Desktop` slot; [V4] the System Events route, with the caveat that System
    Events drops the placement option; [V5] the `allSpaces` option; [V5b] the
    `LastUse` churn across the store; [V5c] a path that does not exist; [V5d] that
    the store file is replaced rather than edited; [V6] the `LastUse` age buckets;
    [V7] a launchd-submitted job in the Aqua session; [V8] the decoded store, with
    `Appearance` absent; [V9] the sandbox comparison, after the fix to the probe's
    own harness recorded below; [V10] `desktoppr`'s install shape. Unverified item
    3, display sleep and wake, was carried this run and passed.
  - not run, with the reason for each:

    - display hotplug and resolution change (item 2): the run was headless, and a

    - what wrote the stale `SystemDefault`, `Displays[...]` and `Spaces['']`

## Config and protocol changes

Checked rather than assumed, against `main`:

- **The config schema did not move.** `config_schema` is `1` in `main` and `1`
  here. No key was added, removed, renamed or given a different default: the set
  of keys `whirl-core` parses is identical in both, as are the two deprecated
  aliases `keep` for `cache.max_files` and `cache_dir` for `cache.root`, and the
  rule that an object key whose first character is `_` is a comment. The keys and
  their defaults are `docs/architecture.md` 4.2, and `whirl config check` prints
  the values a run adopted in its `plan:` line.
- **The protocol version did not move.** `PROTOCOL_VERSION` is `2` in `main` and
  `2` here; the verb list is the same 19 entries and the error-code set is the
  same 21 codes, both in `crates/whirl-core/src/protocol.rs`. One addition is
  visible to a client and is an addition the contract allows: `status` now
  carries `next_at` and `next_in_s`, the persisted deadline and the seconds to it.
  `docs/architecture.md` 2.10 says a key may be added and never renamed or
  removed, and a client must ignore a key it does not know, which is why the
  version did not need to move for it.
- **The state directory did not move.** The config, the state files, the socket,
  the cache and the log are at the paths `docs/spec/state-and-cache.md` 1.1 to 1.3
  give, unchanged from `main`.
- **One CLI verb is new:** `whirl help` prints the usage. It is a CLI arm and not
  a protocol verb, and the socket's grammar is unchanged by it.

## Upgrades and known issues

- **There is no earlier release, so there is nothing to upgrade from.** `git
  ls-remote --tags origin` prints no tags and no release has been published. A
  first-time user installs an archive and is done.
- **What a first-time user has to create: the config file**, at the path `whirl
  config path` prints. The daemon writes an annotated default there when the file
  is missing (`docs/architecture.md` 4.2); the part to fill in is the `sources`
  array, which needs at least one entry naming a folder of your own pictures
  (`docs/quickstart.md` steps 1 to 3). Nothing starts the daemon for you either:
  the archive holds the three binaries and no launchd plist, no Task Scheduler
  registration and no systemd unit, so whirl rotates while `whirld` runs and
  stops when the machine restarts until you start it again
  (`docs/development.md` section 5, "What a release artifact is, per platform";
  `docs/quickstart.md` step 4).
- **Upgrading, once there is an earlier release to upgrade from: stop, replace,
  start.** The daemon is started by the platform supervisor and never by a
  client, so an upgrade is `launchctl bootout`, `schtasks /delete` or `systemctl
  --user stop`, then the binaries replaced in place, then the job started again.
  The caveat that catches people: a **running daemon holds its lock**, and a new
  one refuses to start while the old process holds it, printing the holder's pid,
  so replacing `whirld` under a running daemon is not an upgrade but a second
  daemon failing to start. There is no hot swap and no client-triggered restart,
  and a worker in flight during an upgrade is allowed to die; cache writes are
  temp-file plus rename, so nothing is left half-written
  (`docs/development.md` section 5, "Upgrading, and what happens to a running
  daemon").
- **Known issue: Windows has no setter in this release.** The refusal, the file
  and what a user sees are in the Windows row above. This is the work
  `docs/milestones.md` calls the other two platforms, and it is not in this
  release.
- **Known issue: Linux has no setter in this release.** The same, in the Linux
  row above: one adapter per desktop environment plus the session detection is
  the missing piece.
- **Known issue: a readable JPEG can be counted unreadable.** A `local` source
  measures a file by reading a 1024-byte head window
  (`crates/whirl-worker/src/sources/local.rs`, `candidate()`); a JPEG whose frame
  header sits past that window cannot be measured, so it is dropped and counted in
  the source's `1 unreadable` line. The run behind these notes hit exactly this: a
  perfectly readable file whose frame header starts at byte 3320 was skipped, and
  the source reported 4 candidates where 5 files were readable. If a local
  source's `candidates=` is lower than the folder holds, this is a candidate cause
  before the filters are.
- **Known issue: two defects in the repository's own checklist harness**, both hit
  by the run behind these notes, both in tracked files.
  `docs/research/probes/sandbox_test.sh` builds its entitlements file with a
  `mktemp` template whose `X`s are not last, which BSD `mktemp` refuses, so
  `codesign` ran with an empty `--entitlements` path and the build that was meant
  to be sandboxed was not. `scripts/desktop-restore.sh` cannot restore while
  another store node holds the image that is on screen: its `--holds` step
  refuses when two nodes hold the same file within the same second. The run got
  past the first by putting a GNU `mktemp` first on `PATH` and the second by
  moving the on-screen image to a file no other node held, and neither defect is
  fixed here.
- **Two inaccuracies in `docs/research/macos.md`, recorded so the next reader does
  not think the research observed something it did not.** [V2] quotes
  `com.apple.wallpaper.choice.allSpacesAndDisplays` among the strings in
  `WallpaperAgent`; that string is not in the binary as one piece, where `strings`
  prints `com.apple.wallpaper.choice.helios`,
  `com.apple.wallpaper.choice.image-folder` and a migration line, and `image` and
  `aerials` appear only as bare substrings. The `AllSpacesAndDisplays` node does
  exist, in the store, which is where a store dump reads it. And [V5c] quotes the
  platform's error with a straight apostrophe where the platform prints a curly
  one.
- **Still not run, and still open:** the seven macOS items in the macOS row above
  (multi-display behaviour; hotplug and resolution change; a correctly signed
  sandboxed writer; what wrote the stale store layers; the pre-Sonoma path; the
  semantics of the store's `type`; the never-run-whirl-before machine). Each
  needs hardware or an identity this project does not have, which is why
  `docs/milestones.md` gates the milestone on them rather than on a pipeline.
- **Deferred, not forgotten:** Developer ID signing and notarization for the macOS
  artifact, a `.pkg` or any installer, a Windows signing route, distribution
  packages for Linux (`.deb`, AUR, Flatpak, Snap), and the
  launchd, Task Scheduler and systemd user files that a release will have to
  carry. Each has its decision in `docs/development.md` section 5 and
  `docs/decisions/0001-macos-artifacts-ship-unsigned-in-v0.1.0.md`, and the rest
  of the non-goals are in `docs/spec/features.md` Part 3.
