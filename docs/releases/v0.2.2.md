# whirl v0.2.2

The final release for the daemon the prerelease candidates tested: five fixes to
the rotation path, with no config key renamed, no config key removed, and no
protocol change. It is cut from `main`, which is where all five landed.

Platform support, one line per platform: **supported** means the platform's
release-blocking checklist ran on real hardware, **experimental** means it did
not:

- **support:** macOS is **supported** in this release, and its real-hardware row
  is below. Windows and Linux ship **experimental**: no real-hardware checklist
  was run for either, so the Windows and Linux sections below read `not-run` with
  the reason, and a user on either platform should expect failures. `whirl report
  --checklist windows` (or `--checklist linux`) on the machine that hit one is how
  a report is filed.

The release date and the tagged commit are the tag's, not this file's, which is
why neither is written here: the tag is cut on `main`'s tip after this file lands
there, and `.github/workflows/release.yml` builds the three archives from that tag
and publishes this file as the release notes.

Artifacts, one per platform, each holding the three binaries (`whirld`, `whirl`,
`whirl-worker`) and nothing else:

- `whirl-v0.2.2-linux-x86_64.tar.gz`
- `whirl-v0.2.2-macos-arm64.tar.gz`
- `whirl-v0.2.2-windows-x86_64.zip`

Each archive is published beside its own checksum, the same file name with
`.sha256` appended, written by the same run that built the archive.

## What changed

- **A rotation says it is working before its verdict.** `whirl next`, `whirl
  prev` and `whirl set` (which takes a path or an id) now print one line to
  stderr once the daemon has answered `queued`: `whirl: working; the rotation may
  take up to 300 s`. The worker may run to `schedule.worker_deadline_seconds`, so
  the gap between `queued` and the verdict is the command's normal shape, and a
  client silent through it reads as a command that "just said queued and nothing
  happened" (a failing rotation was measured silent for 78 s). stdout is
  untouched: a harness that reads it sees the same bytes, and nothing about
  `queued` changes on the wire. `config check` carries `queued` too but reports a
  plan rather than a wallpaper, so it is left alone.

- **A photograph whose frame header sits past the head window is measured
  instead of refused.** The download stage kept 1 KiB of head and widened it only
  for bytes that said HEIC, so a JPEG whose APP1/Exif segment runs past that
  window was refused as `not_an_image`: the walk ran out of head and the
  download read that as bad content. The window now widens for any file the small
  window cannot measure, the sniff answers measured, beyond-window or
  not-an-image instead of collapsing the first two, and the beyond-window failure
  names the window as its limit. The same bytes measure under a 64 KiB head, and
  the local source and the download path ask one function for the window, so the
  same bytes get the same verdict from both.

- **A candidate the cache already holds is set without a fetch, and a cache hit
  is the file's bytes hashing to its name.** The cache index maps each source's
  own id to the digest it stored, and a candidate whose bytes are still under
  `sha256/` is now served from the cache with no request to the source (no
  `downloaded:` line is printed for it). A hit is decided by hashing the file's
  bytes against the digest in its name, not by a `stat` or a directory entry, so
  a file something else replaced under the same name is repaired in place rather
  than served, and a genuine hit makes no request. An index that is absent,
  unreadable or of a newer schema leaves the rotation fetching, so a file this
  process only reads cannot fail a rotation.

- **The daemon's log is capped by `log_max_bytes` and trimmed in place.** The log
  was the one file whirl writes with no ceiling: on this machine
  `~/Library/Logs/whirl/whirl.log` measured 1,525,339 bytes over 9,738 lines and
  851 rotations, and the only thing that had ever bounded it was a reinstall. The
  daemon now rewrites the file in place, keeping the newest whole lines, at
  startup and at the end of every rotation, and writes one line saying how many
  bytes it dropped. It trims rather than rotates because the supervisor opens the
  log with `O_APPEND`, which holds the inode and not the path: a rotated file
  would receive the daemon's next line into the archive while the live path went
  quiet.

- **The spec that called the cache hit a `stat` now names the hash.**
  `docs/spec/state-and-cache.md` called the cache hit a `stat` in two places while
  the code decides a hit by hashing the file's bytes against the digest in its
  name. Both sentences now say what the code does: one pass that is also the
  integrity check. Documentation only.

## Config and protocol changes

Checked rather than assumed, against v0.2.1:

- **One config key was added: `log_max_bytes`.** Default `1048576` (1 MiB). It
  caps the daemon's own log file, checked at startup and at the end of every
  rotation: past the cap the daemon rewrites the file keeping the newest whole
  lines. `0` means keep everything and is the only value that means that; any
  other value must be at least `4096`, which is about eight times the widest line
  the daemon writes (484 bytes, the `plan:` line), so a legal cap always has a
  line to drop. The value is read through `reconfigure`, so an edited value
  applies at the rotation that follows the edit rather than at the next daemon
  start. `docs/decisions/0004-the-log-is-capped-and-trims-in-place.md` records
  the decision.
- **One environment variable was added: `WHIRL_LOG`,** the log file
  `log_max_bytes` bounds. It takes the same place in the precedence order as the
  other `WHIRL_*` names (between `WHIRL_CACHE_DIR` and `WHIRL_BACKEND`).
- **The config schema did not move.** `config_schema` is `1` in v0.2.1 and `1`
  here.
- **The protocol version did not move.** `PROTOCOL_VERSION` is `2` in v0.2.1 and
  `2` here; no verb was added and no error code changed.
- **The state directory did not move.** The config, the state files, the socket,
  the cache and the log are at the paths `docs/spec/state-and-cache.md` gives,
  unchanged.
- **One output changed, and it is on stderr only.** `whirl next`, `whirl prev`
  and `whirl set` print one line to stderr when the daemon answers `queued`. A
  reader of stdout sees the same bytes as before; a reader of stderr sees one new
  line.

## Upgrades and known issues

- **Upgrading from any earlier release: stop, replace, start.** That is the whole
  upgrade; nothing in the state directory or the config file has to change. An
  installed daemon keeps the old binary until it restarts, so a running daemon
  holds its lock and a new one refuses to start while the old process holds it:
  stop the daemon you have (`whirl daemon stop`, or the way you started it)
  before replacing `whirld` under it, then start it again.
- **A log follower sees the file rewritten underneath it.** The cap trims the
  single log file in place rather than rotating it, so a `tail -f` that keeps the
  file open across a trim follows the same trade a rotation makes. Nothing may
  look for `whirl.log.1`: there are no rotations.
- **The cap holds where the descriptor appends.** Both supervisors open the log
  with `O_APPEND`, so the cap holds for an installed daemon. A `>` redirect,
  whose descriptor does not append, is the one arrangement the cap is documented
  not to hold for (`crates/whirld/src/log.rs`).
- **Known issue: `whirl daemon install` is macOS only,** unchanged from v0.2.0
  and v0.2.1. On Windows and Linux it prints one sentence naming the platform and
  exits `1`. Those units are deferred, not forgotten.
- **Known issue: the Windows and Linux checklist rows were not run for this
  release** (above); they need real hardware, and this release ships both
  platforms experimental for that reason. A user on either platform should expect
  failures, and `whirl report --checklist windows` or `--checklist linux` on the
  machine that hit one is how a report is filed.
- **Deferred:** the prefetch of the next candidates (implemented and under review,
  and a release does not carry a change nobody has read yet), Developer ID signing
  and notarization for the macOS artifact, any installer or `.pkg`, a Windows
  signing route, Linux distribution packages, and the Task Scheduler and
  `systemd --user` units.
